# 2. ユースケース一覧

## アクター

- Guest: 未認証ユーザー
- Member: 自分の習慣を管理する認証済みユーザー
- Admin: サポート・運用担当。通常ユーザー権限とは分離
- Scheduler: EventBridge から定期処理を開始するシステム
- Worker: SQS メッセージを処理する Lambda
- AI Provider / Email Provider: 外部サービス

## 重要フロー

### オンボーディング

1. Guest が登録し、メールを確認する。
2. Member が IANA タイムゾーンと表示名を設定する。
3. `build` / `reduce` を選び、目標と現在の障壁を入力する。
4. AI 設計案を任意で依頼する。待機中も手動作成を続行できる。
5. ユーザーが提案を確認・修正し、習慣として保存する。
6. 当日の予定なら初回記録へ誘導する。

### 日次記録

1. API がユーザーのタイムゾーンと有効なスケジュールから当日の予定を計算する。
2. ユーザーが成功・未実施・スキップを入力する。`build` で目標回数（target_count）が複数の場合は実施回数（quantity）も入力する。
3. Application 層が所有権、対象日、重複、入力制約を検証する。`build` は quantity が target_count 以上かで成功を判定する。
4. 既存記録があれば更新し、なければ作成する（冪等キーを利用）。
5. 同一トランザクション内の確定データから表示用集計を再計算する。

### 週次レビュー

1. 対象週の予定機会と記録から決定論的な集計を生成する。
2. ユーザーが成果、障壁、自由記述を入力して確定する。
3. AI 分析ジョブをキュー投入する。
4. Worker は必要最小限のデータを匿名化して AI へ送る。
5. 構造化出力を検証し、成功なら提案を保存。失敗なら規則ベースのフォールバックを保存する。
6. ユーザーが提案を閲覧し、採用する変更だけ選択する。

## 例外・競合

- 同じ記録の多重送信: `Idempotency-Key` と一意制約で同じ結果を返す。
- 習慣編集と記録の競合: 楽観ロック用 `version` を確認し、競合は 409。
- AI 停止: ジョブを有限回再試行後 DLQ へ送り、手動レビューと規則ベース提案を表示。
- 通知の遅延: ユーザーの送信許容時間を過ぎたメッセージは送らず expired とする。
- タイムゾーン変更: 変更時点以降の予定に適用。既存の `habit_date` は変えない。
