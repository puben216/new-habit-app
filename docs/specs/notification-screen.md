## 目的

T-401 の `GET/PUT /api/v1/notification-settings` を画面として提供し、Member がリマインドメールの送信時刻・送らない時間帯(quiet hours)・タイムゾーンを設定し、いつでも簡単に停止・再開できるようにする(UC-14)。通知は既定で無効(opt-in)であり、利用者が明示的に有効にしたときだけ後続の配送(T-402)の対象になる。配送そのものは本タスクの対象外。基盤は [web-ui-foundation.md](web-ui-foundation.md)、API は [notification-preferences.md](notification-preferences.md) に従う。

## 成功指標

- Member は `/notifications` で通知を有効にし、送信時刻・quiet hours・タイムゾーンを設定できる(E2E)。
- 停止はワンステップで、設定内容を保持したまま即時に有効になる。再開も同様で、再開時に入力し直す必要がない(E2E)。
- 送信時刻が quiet hours 内の設定は server が拒否し、画面は固定文言で伝える(Unit、E2E)。判定を画面に持たない。
- 未保存の Member には「停止中」と既定値が表示され、画面を開いただけで有効にならない(E2E)。
- 他ユーザーの設定は表示・変更できない(E2E)。

## 範囲

- 画面 `/notifications`(`(onboarded)` 配下)、ナビゲーションに「通知」。
- 状態表示(有効/停止中を文字で表示)と、即時の「通知を停止する」「通知を有効にする(停止後の再開を含む)」。
- 設定フォーム: 送信時刻(`HH:mm`)、タイムゾーン(選択)、quiet hours(なし/あり、開始・終了)。保存は現在の有効/停止の状態を保つ。
- `422` の固定文言表示、二重送信の防止、通信失敗の表示。
- 文書: 本 Spec、Plan、`docs/09`。

## 対象外

- メール送信、送信予定、dedupe、bounce/complaint(T-402)。メール内のワンクリック配信停止は T-402 で別 endpoint として実装済み。本画面はログイン後の設定 OFF のみ。
- 習慣ごとの通知設定、Push/SMS、通知履歴。
- 新規 API・DB の変更(Migration なし)。
- プロフィールの timezone 変更への連動(T-401 の未決事項)。

## 機能要件

### NUI-001 取得と状態表示

- `GET /api/v1/notification-settings` を `useQuery` で取得する。取得中は `loading`、失敗は再試行できる `error`、`401` は共通処理で login へ。
- 現在の状態を文字で表示する: 「リマインドメール: 有効」/「停止中」。未保存(`updatedAt` が `null`)は「停止中(まだ設定していません)」。色だけに依存しない。

### NUI-002 停止と再開

- 有効なら「通知を停止する」、停止中(未保存を含む)なら「通知を有効にする」を表示する。停止後の再開も「通知を有効にする」(設定は保持されているため入力し直しは不要)。
- 押すと、画面に表示中の保存済みの値(送信時刻・timezone・quiet hours)に `enabled` だけを反転して `PUT` する。未保存の編集中の値は使わない。成功したら状態表示を更新し「停止しました」「有効にしました」を `role="status"` で伝える。
- 再開時に server が `422`(`reminder_time_in_quiet_hours`)で拒否したら、固定文言で設定フォームの確認を促す。停止は常に成功する(server の仕様 NPF-003/004)。
- 送信中はボタンを無効化し、同期ロックで二重送信を防ぐ。

### NUI-003 設定フォーム

- 入力: 送信時刻(`type="time"`、必須)、タイムゾーン(選択。取得した値が選択肢にない場合は追加)、quiet hours を設定する(チェック)と開始・終了(`type="time"`)。
- 初期値は GET の値。quiet hours が `null` ならチェックなし、開始・終了は既定の 22:00〜07:00 を入力欄に残す。
- 保存は `PUT`(全項目置換)で、`enabled` は現在の保存済みの状態を保つ。成功で「保存しました」を表示し cache を更新する。
- client 検証(UX): 送信時刻が空、quiet hours を設定するのに開始または終了が空。それ以外(開始=終了、送信時刻が quiet hours 内、timezone の妥当性)は server の `422` を固定文言で表示する。
- `422` は `fieldErrors` のキー(`localTime`、`timezone`、`quietHours` 系)から固定文言を選び、項目直下とエラー要約の両方に出す。`reminder_time_in_quiet_hours` は「送信時刻が送らない時間帯に入っています。」。未知のキーはフォーム全体の固定文言。

### NUI-004 説明文

- 画面で次を伝える: 通知は初期状態で停止していること、送信時刻と送らない時間帯は選択したタイムゾーンのローカル時刻であること、停止してもいつでも再開でき設定は保持されること。メール配信自体の開始時期の約束はしない。

## 業務ルールと不変条件

- NUI-INV-001(業務ロジックを持たない): 時刻の整合(quiet hours 内の拒否、開始=終了の拒否)、timezone の妥当性は server(Domain)が判定する。client は必須の目安のみ。
- NUI-INV-002(opt-in): 画面を開く・保存するだけで有効にならない。有効化は「通知を有効にする/再開する」の明示操作のみ。保存は現在の `enabled` を変えない。
- NUI-INV-003(停止の容易さ): 停止は 1 操作で、フォームの検証に依存しない(未保存の不正な入力があっても停止できる)。
- NUI-INV-004(固定文言): server の文字列を描画しない(WUI-INV-003)。
- NUI-INV-005(個人情報の非ログ): 設定値をログ・URL・storage に出さない。
- NUI-INV-006(所有者限定): 画面は `/notification-settings` のみ。対象ユーザーを指定する手段がない。

## 状態遷移

| 現在の状態    | 操作                | 次の状態           | 拒否される条件                           |
| ------------- | ------------------- | ------------------ | ---------------------------------------- |
| 停止中/未保存 | 有効にする/再開する | 有効               | `422`(送信時刻が quiet hours 内、不正値) |
| 有効          | 停止する            | 停止中(設定保持)   | なし                                     |
| 有効/停止中   | 設定を保存          | 同じ状態(値を更新) | `422`                                    |

## 受け入れ基準

```gherkin
Scenario: 未保存の Member は停止中として既定値を見る
  When /notifications を開く
  Then 「停止中(まだ設定していません)」と既定の送信時刻 20:00、quiet hours 22:00〜07:00 が表示される
  And GET 後も DB に行は作られず、有効にもならない

Scenario: 通知を有効にして設定する
  When 送信時刻 07:30 に変更して保存し、「通知を有効にする」を押す
  Then 「リマインドメール: 有効」と表示され、再読み込み後も 07:30 と有効が保持される

Scenario: 停止と再開は設定を保持する
  Given 有効で送信時刻 07:30 の Member
  When 「通知を停止する」を押す
  Then 「停止中」と表示され、送信時刻 07:30 は保持される
  When 「通知を有効にする」を押す
  Then 有効に戻り、入力し直す必要がない

Scenario: 送信時刻が送らない時間帯内
  When 送信時刻を 23:00(quiet hours 22:00〜07:00)にして保存する
  Then 固定文言のエラーが項目と要約に表示される
  And 停止中なら保存は成功する(停止中は組み合わせ検査をしない)

Scenario: 保存しても有効にならない
  Given 停止中の Member
  When 設定を保存する
  Then 停止中のまま

Scenario: 不正な入力
  When 送信時刻を空にして保存する、または quiet hours を設定して開始を空にする
  Then request は送られず、固定文言のエラーが表示される

Scenario: 他ユーザーの設定は見えない
  Given Member A が有効な設定を保存している
  When Member B が /notifications を開く
  Then B 自身の設定(停止中・既定値)が表示される
```

## APIとイベント

新規・変更なし。`GET/PUT /api/v1/notification-settings`(T-401)を型付き client で消費する。`PUT` は同一 origin の fetch でブラウザが `Origin` を付け、server が検証する。

## 失敗・境界ケース

- 取得失敗: エラー表示と再試行。保存・切り替えの通信失敗: 固定の通信失敗文言(入力は保持)。
- 停止/再開は保存済みの値を送る。画面に未保存の編集があっても、停止/再開はそれを送らず、編集は保持される。
- 再開が `422` で拒否された場合: 状態は停止中のまま、固定文言で設定の見直しを促す。
- timezone が選択肢にない値: 現在値を選択肢に加える。
- 別タブでの更新: last-write-wins(NPF-INV-002)。保存後は応答で画面を更新する。

## セキュリティとプライバシー

- 収集データ: 通知の有効/無効、時刻、timezone(既存)。外部送信なし。ログ禁止: 設定値。
- IDOR は API の所有者限定(E2E で 2 ユーザー)。CSRF は server の Origin 検証。XSS: 表示するのは固定文言と数値/時刻のみ。
