## 目的

T-104 の `/api/v1/habits` を画面として提供し、Member が習慣(build/reduce)を作成・一覧・編集(詳細とスケジュール)・アーカイブできるようにする。更新競合(409)では、利用者が入力を失わずに最新の内容を読み込み直せる導線を持つ。基盤は [web-ui-foundation.md](web-ui-foundation.md)、API は [habit-api.md](habit-api.md)、業務ルールは [habit-domain.md](habit-domain.md) に従う。

## 成功指標

- build と reduce の習慣を UI だけで作成・編集・アーカイブできる(E2E)。
- 他のユーザーの習慣は一覧にも詳細にも現れず、URL を直接指定しても「見つかりません」になる(E2E)。
- 古い `version` での更新(409)で、競合を伝える固定の文言と「最新の内容を読み込む」操作が表示され、読み込み後に再度保存できる(E2E)。
- 業務ルール(reduce の回数固定、遡及編集の拒否等)の判定を画面に持たず、server の `422` を固定文言で表示する(Unit、E2E)。
- 二重クリックで作成・アーカイブが重複しない(E2E)。

## 範囲

- 画面: `/habits`(一覧。active/archived の切り替え、さらに表示)、`/habits/new`(作成)、`/habits/[habitId]`(詳細・編集・アーカイブ)。
- 作成: kind(build/reduce)、名前、目的、きっかけ、最小の行動、代わりの行動(reduce のみ)、スケジュール(適用開始日、曜日、回数(build のみ))。
- 編集: 詳細項目、スケジュール(新しい適用開始日から新しい版を追加)。`kind` は変更不可。
- アーカイブ(2 段階の確認)。アーカイブ済みは閲覧のみ。
- 更新競合(`version_conflict`)とアーカイブ済み(`habit_archived`)の導線。
- 「今日」の日付はプロフィールの timezone から client が算出して適用開始日の既定にする(habit-api.md HAPI-001)。
- ナビゲーションへ「習慣」を追加。

## 対象外

- 新規 API・DB の変更(Migration なし)。`localTime`、リマインド時刻。
- 習慣の削除(物理削除)、並べ替え、検索・絞り込み。
- 記録の入力(T-215)、集計の表示(T-216)。
- スケジュール履歴(過去の版)の編集。詳細画面では現在有効な版と履歴の閲覧のみ。
- 文字数上限の確定(P2)。client は契約 schema の暫定定数を目安に使う。

## 機能要件

### HUI-001 一覧

- `/habits` は `GET /api/v1/habits?status=…` を `useInfiniteQuery` で取得し、名前・種別(build/reduce のラベル)・曜日の要約・状態を表示する。各行は詳細へのリンク。
- 状態の切り替え(進行中/アーカイブ済み)は `status` クエリで行い、現在の選択に `aria-current` を付ける。
- `nextCursor` があれば「さらに表示」を出す。空なら空状態と「習慣を作る」への導線。取得失敗は再試行できるエラー表示。

### HUI-002 作成(`/habits/new`)

- 種別の選択(radio、必須)。reduce を選ぶと回数欄を出さず(1 固定)、代わりの行動の欄を出す。build は回数(1〜100)を出す。
- 入力: 名前、目的、きっかけ、最小の行動(いずれも必須)、適用開始日(既定は今日)、曜日(1 つ以上)。
- 送信は `POST /api/v1/habits`。成功したら詳細画面へ遷移し、一覧の cache を無効化する。
- client 検証(UX): 必須、上限(名前 100 / 他 500 文字の目安)、曜日 1 つ以上、回数の範囲。それ以外(制御文字、reduce の規則、遡及等)は server の `422` を固定文言で表示する。

### HUI-003 詳細・編集(`/habits/[habitId]`)

- `GET /api/v1/habits/{id}` を取得し、詳細項目とスケジュールを編集フォームに表示する。種別は読み取り専用で表示する。
- 現在有効なスケジュール(`effectiveTo` が `null` の版)の曜日・回数を初期値にする。スケジュールの履歴は一覧で閲覧のみ。
- 保存は `PATCH`。変更した項目だけを送る(詳細の変更とスケジュールの変更は 1 回の request)。スケジュールは変更があるときだけ `schedule`(適用開始日、曜日、回数)を送る。変更がなければ保存は「変更がありません」を表示し request を送らない。
- スケジュール変更の適用開始日は入力欄(既定は今日)。server が遡及(既存版の開始日以前)を `422`(`schedule.effectiveFrom`)で拒否したら、固定文言「適用開始日は、現在のスケジュールの開始日より後の日付にしてください。」を表示する。
- 存在しない・他ユーザーの習慣・UUID でない ID は、同一の「習慣が見つかりません」表示(`404`)とし、一覧への導線を出す。

### HUI-004 更新競合とアーカイブ済み

- `409 version_conflict` では、入力内容を保持したまま固定文言「他の場所で更新されました。最新の内容を読み込んでから、もう一度保存してください。」と「最新の内容を読み込む」ボタンを出す。ボタンは再取得して `version` と表示を最新にし、フォームを最新の値に置き換える(利用者の入力は破棄されることを文言で伝える)。
- `409 habit_archived` では、アーカイブ済みである旨を示して読み込み直す(以後は閲覧のみ)。
- 保存の送信は `version`(取得時点の値)を必ず付ける。

### HUI-005 アーカイブ

- 「アーカイブ」を押すと確認(「この習慣をアーカイブしますか。進行中の一覧から外れます。」と「アーカイブする」「やめる」)を同じ画面に出す。確定で `POST …/archive`(`version` 付き)を送る。
- 成功したら `/habits` へ遷移し、cache を無効化する。`409 version_conflict` は HUI-004 と同様。再実行(既にアーカイブ済み)は server が冪等に成功する。
- アーカイブ済みの習慣の詳細は編集欄を無効化し、「アーカイブ済み」を示す。

### HUI-006 共通

- 表示するエラーはすべて固定文言(server の `message`/`fieldErrors` の文字列は描画しない)。項目の `fieldErrors` キー(`name`、`purpose`、`cue`、`minimumAction`、`replacementAction`、`schedule`、`schedule.effectiveFrom`、`schedule.daysOfWeek`、`schedule.targetCount`)から固定の文言を選び、項目直下と要約の両方に出す。未知のキーはフォーム全体の固定文言。
- 送信中はボタンを無効化し二重送信しない。ナビゲーションに「習慣」(`/habits`)を追加する。

## 業務ルールと不変条件

- HUI-INV-001(業務ロジックを持たない): kind 不変、reduce の回数固定、遡及編集の拒否、有効期間の重複禁止は server(Domain)が判定する。client は入力の目安の検証と、種別に応じた欄の出し分けのみ。
- HUI-INV-002(所有者限定): 画面は `/api/v1/habits` だけを使い、他ユーザーの習慣を取得・表示する手段を持たない。
- HUI-INV-003(version の送信): 更新・アーカイブは取得時点の `version` を必ず送る。競合時に `version` を勝手に最新へ置き換えて再送しない(利用者が読み込み直す)。
- HUI-INV-004(server 文言の非描画): AUI-INV-002 と同じ。
- HUI-INV-005(個人情報の非ログ): 習慣の名前・目的・きっかけをログ・URL・storage に出さない。

## 状態遷移

| 現在の状態 | 操作                  | 次の状態          | 拒否される条件                           |
| ---------- | --------------------- | ----------------- | ---------------------------------------- |
| (なし)     | 作成                  | active            | 検証違反(`422`)                          |
| active     | 詳細/スケジュール保存 | active(version+1) | `422`、`409 version_conflict`            |
| active     | アーカイブ            | archived          | `409 version_conflict`                   |
| archived   | 保存                  | (変更なし)        | `409 habit_archived`(画面は編集を無効化) |
| archived   | アーカイブ(再実行)    | archived          | なし(冪等)                               |

## 受け入れ基準

```gherkin
Scenario: build の習慣を作成する
  Given オンボーディング完了済みの Member
  When /habits/new で build を選び、名前・目的・きっかけ・最小の行動・曜日・回数を入力して保存する
  Then 詳細画面へ遷移し、入力した内容が表示される
  And /habits の一覧に表示される

Scenario: reduce の習慣は回数を入力せず作成できる
  When reduce を選ぶ
  Then 回数欄は表示されず、代わりの行動の欄が表示される
  When 保存する
  Then 作成され、スケジュールの回数は 1 である

Scenario: 入力エラー
  When 必須項目を空にする、または曜日を 1 つも選ばずに保存する
  Then request は送られず、項目と要約に固定文言のエラーが出て要約にフォーカスが移る

Scenario: 詳細とスケジュールを編集する
  Given 作成済みの習慣
  When 名前を変更して保存する
  Then 保存され、再読み込み後も変更が残る
  When 適用開始日を翌日にして曜日を変更して保存する
  Then 新しいスケジュールが履歴に追加される

Scenario: 遡及的なスケジュール変更は固定文言で拒否される
  Given 今日が適用開始日のスケジュールを持つ習慣
  When 適用開始日を今日のまま曜日を変えて保存する
  Then 「適用開始日は、現在のスケジュールの開始日より後の日付にしてください。」が表示される

Scenario: 更新競合
  Given 同じ習慣を 2 つのタブで開いている
  When タブ A で保存した後、タブ B で保存する
  Then タブ B に競合の固定文言と「最新の内容を読み込む」が表示され、入力は保持される
  When 「最新の内容を読み込む」を押す
  Then タブ A の変更が表示され、再度保存できる

Scenario: アーカイブ
  When 「アーカイブ」→「アーカイブする」を押す
  Then /habits へ戻り、進行中の一覧から消え、アーカイブ済みの一覧に表示される
  And アーカイブ済みの詳細は編集できない

Scenario: 他ユーザーの習慣は見えない
  Given Member A の習慣
  When Member B がその詳細 URL を開く、または一覧を開く
  Then 「習慣が見つかりません」が表示され、一覧に A の習慣は出ない

Scenario: 二重クリック
  When 保存ボタンを素早く 2 回押す
  Then 作成の request は 1 回だけ送られる
```

## APIとイベント

新規・変更なし。`GET/POST /api/v1/habits`、`GET/PATCH /api/v1/habits/{id}`、`POST /api/v1/habits/{id}/archive`(T-104)を型付き client 経由で消費する。変更系は同一 origin の fetch でブラウザが `Origin` を付け、server が検証する。

## 失敗・境界ケース

- 一覧・詳細の取得失敗: エラー表示と再試行。`401` は共通処理で login へ。
- `404`: 「習慣が見つかりません」(UUID でない ID も同じ)。
- 通信失敗: 固定の通信失敗文言。入力は保持する。
- 一覧の `cursor` 不正(`422`)は発生しない設計(client は server が返した値だけを使う)。想定外なら再読み込みを促す。
- timezone が不正・取得できない場合の「今日」: プロフィールの取得失敗はエラー表示とし、日付を推測しない。
- 同じ日に作成した習慣のスケジュールを同日に変更する場合は遡及扱いで拒否される(固定文言で案内)。

## セキュリティとプライバシー

- 収集データ: 習慣の名前・目的・きっかけ等(既存)。外部送信なし。
- ログ禁止データ: 習慣の自由記述、body。
- 脅威と対策:
  - IDOR: `/api/v1/habits` の所有者限定に依存し、画面は ID を path で受けるだけ(E2E で 2 ユーザーを確認)。
  - XSS: 自由記述は React のエスケープで描画。E2E で HTML 文字列が文字として表示されることを確認する。
  - CSRF: 変更系は server の Origin 検証(T-104)。
  - 競合による上書き: `version` を必ず送り、勝手に最新へ置換しない(HUI-INV-003)。
